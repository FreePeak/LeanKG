# Cross-Tool Agent A/B Benchmark

A codegraph/graphify-style headless-agent benchmark. A fixed `claude -p`
(Claude Code) agent answers one architecture question on seven real-world
codebases, under three arms:

| Arm | Tools the agent gets |
|---|---|
| `baseline` | built-in Read/Grep/Bash only (`--bare`, no MCP) |
| `context-mode` | built-in tools + the context-mode MCP server, pinned in `tools.lock.yaml` |
| `leankg` | built-in tools + the LeanKG MCP server (`leankg serve --stdio`) |

Numbers are comparable in method to `colbymchenry/codegraph`'s published 7-repo
suite (re-validated 2026-07-21, Opus 4.8); the questions come from that suite.
The byte metric follows context-mode's own method (raw tool-output bytes vs
bytes delivered to the model, tokens = bytes / 4), and answer quality is scored
judge-blind.

Status: setup and dry run only. A real run needs user approval and a filled-in
`tools.lock.yaml`; see [RUNNING.md](RUNNING.md).

## What we measure (per trial, per arm, per repo)

| Metric | Source |
|---|---|
| Tool calls | `tool_use_count` from the `claude -p --output-format json` envelope |
| Wall-clock time | `time` around the `claude -p` call (`duration_s`) |
| File reads | `file_read_count` from the envelope |
| Input / output / cache-read tokens | `usage.input_tokens`, `usage.output_tokens`, `usage.cache_read_input_tokens` |
| Bytes delivered to the model | `tool_result_bytes`: sum of `tool_result` content in the transcript; tokens estimated as bytes / 4 |
| Bytes the raw output would have put in context | not recorded yet; see RUNNING.md (needs per-arm instrumentation) |
| Cost | `total_cost_usd` |
| Exit reason | `stop_reason`, `exit_code` |
| Answer quality | `score.py`, judge-blind 0-6 rubric (`make score`) |

The aggregator (`aggregate.py`) reports the **median** of N trials per arm per
repo, matching codegraph's methodology. IQR is shown in an appendix. The
aggregator takes its arms from the rows (one column group per arm, with
bytes-in-context reduction vs baseline and a losing-rows section); see RUNNING.md.

## Quick start (no agents, no API)

```bash
# from the repo root
make go-build                                              # bin/leankg
make -C benchmarks/cross_tool lock                         # repos.lock.yaml
make -C benchmarks/cross_tool dry-run MODEL=<pinned id>    # plan + blockers
make bench-cross-tool                                      # same plan, via the root Makefile
```

`make dry-run` lists every blocker that stops a real run (placeholder pins,
missing clones, missing context-mode server, old node). The real-run targets
run the same check and refuse to start while a blocker applies to their arm.

Real runs are described in [RUNNING.md](RUNNING.md). Do not start one without
the approval listed there.

## Rigor (FR-ZCP-08)

The harness hardens the codegraph methodology on five axes, and the report
computes each gate from run metadata (see the **Rigor Checklist** section of any
generated report):

| Pitfall | Guard | Where |
|---|---|---|
| Corpus drift (leakage of "different codebase" into the comparison) | refs are resolved to **40-hex commit SHAs** by `make lock` and frozen in `repos.lock.yaml`; `run_arm.sh` refuses to run when the clone HEAD != locked SHA; `plan.py` reports drift before a run | `clone_repos.py`, `run_arm.sh`, `plan.py` |
| Prompt drift (like-for-like) | every prompt has a `prompt_version`; each JSONL row records the prompt's SHA-256; a report cell mixing prompt hashes is flagged | `repos.yaml`, `run_one.sh`, `aggregate.py` |
| Model drift | a real run requires `MODEL` to equal the pinned `model.id` in `tools.lock.yaml`; an empty model (CLI default) is refused | `plan.py`, `Makefile` |
| Stochasticity | **>=3 valid trials per arm** enforced by the trials gate (default N=4); IQR appendix makes variance visible; runs where the judge failed are excluded | `aggregate.py` |
| Tool-access smoke | an MCP arm run is invalid unless the session init event shows **>=1 reachable `mcp__` tool**; the baseline run with any MCP server attached is void (`mcp_leaked_into_baseline_arm`) | `run_one.sh` |
| Judge bias (answer quality) | `score.py` grades answers on a 0-6 rubric **judge-blind**: answers are shuffled, relabeled A/B/C..., and the judge prompt contains only the question + answers, never the arm label | `score.py` |

```bash
# after the arms:
make score     # judge-blind quality scoring (needs claude CLI)
make report    # medians + variance + quality + rigor checklist
```

## Methodology notes

- Same prompt per repo for all three arms. Prompts come from `repos.yaml`
  (codegraph-derived where applicable), so numbers stay comparable.
- Each `claude -p` invocation uses `--strict-mcp-config`, so no arm inherits the
  user's global MCP setup. The `leankg` arm config registers
  `leankg serve --stdio` from the repo-root build; the `context-mode` arm
  registers the pinned context-mode `server.mjs`; the `baseline` arm config is
  `{"mcpServers": {}}` with `--bare`.
- For every `leankg` trial the index is rebuilt (`leankg index .`) after `rm -rf
  .leankg`, so runs start from the same store. `leankg index` also runs the
  embed step unless `--no-embed` is given; see RUNNING.md before a real run.
- Built-in `Read`/`Grep`/`Bash` stay available to all three arms.
- `claude -p --output-format json` returns an event array whose last element is
  the result; `run_one.sh` parses it in Python for robustness against CLI
  version drift.
- Median of N=4 trials is reported per arm per repo (matches codegraph);
  >=3 valid trials per arm are required for a row to pass the trials gate.
- The model is pinned in `tools.lock.yaml`. The Makefile no longer defaults to
  `sonnet`: an empty model is refused, so the choice is recorded, not implied.

## Caveats

- Self-reported single-vendor benchmark. Treat as best-case.
- Larger repos dominate the mean; we report medians for transparency.
- The `leankg` and `context-mode` arms run without `--bare`, so the user's global
  CLAUDE.md, hooks and plugins load into those arms, while `baseline` runs
  hermetically. That confound is pre-existing and is not fixed by this setup
  (see RUNNING.md, approvals).
- Variance on the `baseline` arm can be high because the agent has no structured
  index to lean on; IQR in the appendix makes that visible.
- Indexing cost is not part of the agent invocation. The index is rebuilt once
  per `leankg` trial for fairness. To measure incremental indexing separately,
  see `leankg writer --project <dir>`.
